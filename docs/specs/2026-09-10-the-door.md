# The door

**Status:** Draft (2026-09-10)
**Plan:** §4.4 phase 3 — "Auth surfaces: login, register, invite redemption…
The front door ships with identity, not after it." §4.5 UI invariants.
**Depends on:** ADR 0003 (AGPL-3.0, and therefore §13).

## Problem

`server/templates/landing.html` sells Brolly. It opens "One account. Your data
lives in your pod, and every protocol reads the same graphs," lays out three
cards headed *Solid*, *ATProtocol* and *ActivityPub*, and closes on a band that
says "Bring your data home."

That is product copy, and brolly-server is not a product page. One image serves
many deployments — the admin-console spec already made the instance's own
identity configuration for exactly this reason. The landing page took the
`{{ instance_name }}` heading and kept the pitch underneath it, which is the
worse half to keep: a housing co-op that stands up an instance gets its own name
at the top of a page arguing for somebody else's software.

The marketing has a home already, and it is not here: brolly.id keeps
`marketing-site` as a separate application behind nginx, apart from the member
app and the admin app. The apex sells; the server opens the door.

Four smaller things fall out of the same look:

- **`instance_description` has never been rendered.** It is read by
  `server/src/mastodon_api.rs:141` and `:156` for `/api/v1/instance`, and by
  nothing else. A Mastodon client knows what the instance calls itself; a person
  visiting it in a browser does not.
- **The footer is the last hardcoded `"Brolly"`.** `server/templates/base.html:28`
  reads `Running <a href="https://github.com/">Brolly</a> — a Solid pod, an
  ATProto PDS, and an ActivityPub server over one triplestore.` It names the
  product, it is the protocol advertisement in miniature, and its link goes to
  GitHub's *homepage* — which is today's only discharge of the AGPL network
  clause, and discharges nothing.
- **The umbrella is a brand mark.** `server/static/brolly.png` is Brolly's, and
  a co-op's front page showing it is the branding this spec exists to remove.
- **There are two unauthenticated layouts.** `landing.html` is a full-bleed
  band; `auth.html` is a card inside the shell chrome. Registering means
  crossing between them, and the seam is visible.

## Goals

1. Nothing on the unauthenticated surface names Brolly, or says anything an
   operator did not configure.
2. `instance_description` reaches a human.
3. One unauthenticated layout, not two.
4. The §4.5 invariants keep passing without being edited to accommodate this.

## Non-goals

- **No operator-authored content.** No markdown blurb, no editable landing copy,
  no admin-console content surface. The instance name and one line of
  description are the whole vocabulary. An operator who wants to say more puts a
  marketing site in front, the way brolly.id does.
- **No protocol advertisement.** What this server speaks is already answered, in
  machine-readable form, by NodeInfo and `.well-known`. A prose restatement on
  the front page is marketing wearing a documentation hat. This does **not**
  extend to the authenticated surface: `account/overview.html:22`,
  `account/profile.html:18` and `admin/overview.html:40` name protocols because a
  member needs to know where to point a Solid app. That is instruction, not
  advertisement, and it stays.
- **No open registration.** Out of scope here and unchanged: `register_page`
  states the instance is invite-only and the form takes an invite code
  (`server/src/auth.rs:159`, `:164`). There is no toggle, so the door has no
  second registration state to render.
- **No configurable favicon.** See "The favicon stays" below.
- **No off-apex change.** See "Off-apex" below.

## Design

### Unauthenticated is the door; authenticated is the shell

A chromeless two-panel field for anyone not signed in, and the existing header +
tabs shell once they are. The split is the whole information architecture, and
it is what removes the seam between landing and login.

The door: no header, no footer. The left panel is `--wash`, and carries the
instance name, the description, and the fine print pinned to its foot. The right
panel is paper, and carries the form. Below the two-column breakpoint the panels
stack, name above form, and the fine print moves to the bottom of the page —
pinning it under the colour panel when that panel is a header would put the
legal links between the description and the form the visitor came for.

There is no header to hold a brand link because the left panel *is* the brand
link's content, at display size. That was the observation that killed the
chrome: on a page whose only job is to say what this instance is and let you in,
a header repeating the instance name is the same words twice.

### The instance name is the `<h1>`; the form heading becomes `<h2>`

`auth.html` today has exactly one `<h1>`, and it is `{{ heading }}` — "Log in",
"Create your account". The door adds the instance name at display size, and
`every_template_has_one_h1_and_a_main_landmark` counts `<h1>` occurrences
textually (`server/tests/ui_invariants.rs:208`), conditionals included. Two
`<h1>`s fails it.

The instance name takes the `<h1>` and `{{ heading }}` drops to `<h2>`. The page
is *this instance*; logging in is what you do on it. That also matches the
heading order a screen reader announces when the panels stack — name, then form.

`.auth-card h1` (`server/static/brolly.css:337`, damping the heading to
`--txt-1`) stops matching. It is **not** renamed to `.auth-card h2`: that
selector is shared with `consent.html:8`, which keeps its `<h1>`, and renaming
it would silently drop the consent screen's heading to the global `h1` size
(`--txt-2`, `brolly.css:98`). It is also unnecessary — the global `h2` rule
(`:99`) is already `--txt-1`, so the door's form heading lands where the old
rule put it. So the `.auth-card` rules are left **entirely alone** — the door
gets its own classes and `consent.html` keeps the card it still uses. Nothing
about `.auth-card` moves, merges or is renamed.

### One template, three routes

`auth.html` is already a generic form: `heading`, `intro`, `error`, `action`,
`fields[]`, `submit`, and an alt-link, driven by `AuthPage`
(`server/src/auth.rs:87`). Login and register already share it. Restructuring it
into the door therefore gets `/register` for free.

| Route | Renders | Notes |
|---|---|---|
| `GET /` | the door, login fields | `get(auth::login_form)`, replacing `views::landing` |
| `GET /login` | the door, login fields | the same handler, new layout |
| `POST /login` | unchanged apart from its redirect, below |
| `GET /register` | the door, register fields | invite code, as today |
| `POST /register` | unchanged apart from its redirect, below |

`landing.html` is deleted. `views::landing` was the only item in
`server/src/views.rs`, so the file goes and `pub mod views;`
(`server/src/lib.rs:28`) with it.

`/` and `/login` rendering the same thing is deliberate rather than tidy.
Collapsing them into one route would mean re-pointing every redirect that
targets the login form, and there are five: `require_session`
(`server/src/account.rs:71`), `server/src/solid_oidc.rs:264`,
`server/src/mastodon_oauth.rs:281`, `server/src/atproto_oauth.rs:276` and
`server/src/admin.rs:84`. Those are the fiddliest flows in the workspace. Two
routes over one template costs a line in the router and touches none of them.

Both routes point at `auth::login_form`, which is what makes the byte-identity
assertion below hold: `login_action(None)` yields `"/login"` either way, so the
form posts to the same place from both.

Because `auth.html` titles itself `{{ heading }} — {{ instance_name }}`, the
instance's home page will carry `<title>Log in — Fernwood Housing Co-op</title>`.
That is a real consequence of one template, and it is the right one: an
anonymous visitor's business at `/` is logging in.

### The handlers gain a session read

This is the part that actually changes behaviour, and it is not free.
`login_form` (`server/src/auth.rs:188`) is
`(State<AppState>, Query<Next>)` and `register_form` (`:248`) is `(State<AppState>)`
— **neither takes a `CookieJar`, and neither reads a session at all.** Bouncing
a signed-in visitor therefore means adding a `CookieJar` extractor and a session
lookup to both, in the shape `require_session` already uses in
`server/src/account.rs`.

`AuthPage` (`:87`) already carries `instance_name` (`:88`) — that is why
`auth.html:3` can title itself `{{ heading }} — {{ instance_name }}`. It gains
`instance_description` and the three link fields, and both `login_page` (`:125`)
and `register_page` (`:150`) supply them.

### Redirects

A signed-in visitor gets 303 to `/account` from both `/` and `/login`. A login
form is not an answer to a request from somebody already logged in.

Four sites point at `/` today. Two are re-aimed and two are correct as they
stand:

| Site | What it is | Disposition |
|---|---|---|
| `server/src/auth.rs:211` | successful login, no `next` | → `/account` |
| `server/src/auth.rs:358` | session created after registration | → `/account` |
| `server/src/auth.rs:393` | `logout` (fn at `:386`) | stays `/` — the user is anonymous, so `/` is the door |
| `server/src/account.rs:536` | tail of **`delete_account`** (fn at `:499`), not logout | stays `/` — same reason, and there is no account left to land on |

One more, in a template rather than a handler: `base.html:17` is
`<a class="brand" href="/">{{ instance_name }}</a>`, the only `href="/"` in
`server/templates/`, and it sits on every authenticated page. Once `/` bounces
signed-in visitors, every click of it from the dashboard is a guaranteed
double-hop. It is re-pointed at `/account`, which is also what a signed-in
person means by "home".

### Off-apex

`/` is **not** apex-gated — it is registered at `server/src/lib.rs:108`, outside
the `apex_only` layer applied at `:104`. So the door renders on member
subdomains too, and `alice.brolly.id/` will show a login form headed with the
*instance* name.

That is exactly what `landing.html` does today, so this spec changes nothing
about it and does not depend on ADR 0010. It is worth writing down because ADR
0010's consequences promise that `GET alice.brolly.id/` is "a server-rendered
profile page, not her LDP root container" — that page is unbuilt, and when it is
built it replaces the door off-apex. Listed under Open questions.

### Chrome becomes two blocks

`base.html` wraps `.shell-header` and `.shell-footer` in `{% block header %}`
and `{% block footer %}`; the door overrides both with nothing. `<main>` and the
skip link stay in `base.html` unconditionally.

This is the load-bearing choice for the test suite. A separate `base-door.html`
would be collected by `collect_templates`, which skips only `base.html` and
`_`-prefixed partials, and would then fail
`every_template_has_one_h1_and_a_main_landmark` for having no `<h1>`. Blocks on
the existing base keep every invariant green without an edit to
`server/tests/ui_invariants.rs`, and the door keeps a skip target.

Likewise `every_page_template_uses_the_page_container`: `auth.html` already
carries `class="wrap"`, and it stays, inside the right panel. It is not a token
gesture — `.wrap` caps the measure at `--grid-max-width` and centres it, which
is real work on a wide display where a half-width panel is still over a thousand
pixels.

### The fine print, and the footer that shares it

Three links at the foot of the colour panel, labelled **Source**, **Terms** and
**Privacy**. Two are optional and one is not.

`BROLLY_TERMS_URL` and `BROLLY_PRIVACY_URL` are unset by default and the
corresponding link is omitted entirely when they are — an instance with neither
gets a clean panel rather than two links to nowhere.

The source link always renders, and its visible text is "Source" rather than a
product name, which is now banned from this template anyway. ADR 0003 chose
AGPL-3.0 deliberately — its Decision records that "the licence is not a cost we
are absorbing to get a dependency — it is the intended posture" — so §13 binds,
and an operator running a modified copy owes their users the source. A link from
the page every user reaches is the cheapest possible discharge, so
`BROLLY_SOURCE_URL` has a compiled-in default and an operator running a fork
points it at theirs. It has no "unset" behaviour because a licence obligation
does not have one.

**`base.html`'s footer is in scope, for the same reason.** It is the other page
every user reaches, its current link is the §13 discharge and points at GitHub's
homepage, and it carries the last hardcoded `"Brolly"` and the last protocol
advertisement. It becomes the same three links, plus the existing "Your data
lives in your pod. Take it with you whenever you like." line, which says nothing
about the software's name.

One `_fine_print.html` partial serves both surfaces; the `_` prefix keeps it out
of `collect_templates`, which is correct because it has no `<h1>`. The two
surfaces style it differently — in the footer the links inherit `.shell-footer a`
(`brolly.css:204`, underlined via `border-block-end`); on the door's wash panel
they need their own rule, including the focus treatment below.

### The focus ring on a field of colour

`brolly.css:121` carries `.band :focus-visible` with a comment that explains
itself: "Inside a flat field of colour the brand blue is only 2.1:1 against the
wash, so a keyboard user tabbing into the hero would barely see where they are…
the ring borrows [the foreground] instead of the token — one rule that stays
correct for every wash, in both themes."

`.band` is deleted below. The door's left panel **is** `--wash` and carries
three links, so the arm is not a casualty of that deletion — it moves. The list
is three arms today (`.band`, `.card-feature`, `.notice`) and becomes two: the
door's name panel and `.notice`. `.card-feature` goes with it, because that
class dies with `landing.html` as well. Missing this reintroduces a 2.1:1 focus
ring on the only links on that panel, in both themes.

### Configuration plumbing

Three fields, following `BROLLY_INSTANCE_NAME` (`server/src/main.rs:62`) and
`BROLLY_INSTANCE_DESCRIPTION` (`:66`) exactly:

| Variable | Required | Default |
|---|---|---|
| `BROLLY_SOURCE_URL` | no | a compiled-in constant naming the upstream repository |
| `BROLLY_TERMS_URL` | no | none; the link is omitted |
| `BROLLY_PRIVACY_URL` | no | none; the link is omitted |

Read in `main.rs`, carried on `AppState` (`server/src/lib.rs:49` is where
`instance_description` already sits), documented in the table in
`docs/deploying.md` and in `docs/running-locally.md`.

### Themes and tokens

No new tokens. The left panel is `--wash` / `--wash-fg` and the right is
`--background` / `--foreground`, all four already defined in both themes —
`natt` resolves `--wash` to `#1f3d54` with light text, which is where the
contrast comes from without a second colour decision.

Borders are `--border-width` (3px, `batklubb.config.js:198`) and `--hairline`
(1px, `:199`), already generated. `tokens.css` is generated and
`the_token_file_is_never_hand_edited` enforces it; nothing here touches either.

### What becomes dead, and goes

`landing.html` is the only user of all of this, so deleting it strands the lot:

- `server/static/brolly.png`, referenced only from `landing.html:37`. Note that
  `every_stylesheet_url_resolves_to_a_shipped_file` does **not** cover it — that
  test scans `url("…")` in CSS (`ui_invariants.rs:249`), and this is an
  `<img src>`. Removing the asset is a deliberate step, not something a test
  will remind us about.
- In `server/static/brolly.css`: `.band` (`:211`), `.band-hero` (`:212`),
  `.band-invite` (`:213`), the `.shell-main > .band:last-child` rule with its
  explanatory comment (`:185–192` — taking `:186–192` alone leaves an
  unterminated `/*`) and the `.shell-main:has(> .band:last-child)` rule (`:218`),
  `.hero`, `.hero h1`, `.hero .lede`, `.hero-figure`, `.hero-figure img`
  (`:221–240`), `.card` (`:299`), `.card-grid` (`:294`), `.card h2` (`:308`),
  `.card p` (`:309`), `.card-feature` (`:311`), `.button-compact` (`:277`, whose
  only consumer is `landing.html:8`), and the `.band :focus-visible` and
  `.card-feature :focus-visible` arms at `:121–122` — the first of which
  **moves** to the door panel rather than dying, per the section above.
- In `batklubb.config.js`: `wash-invite` / `wash-invite-fg` in both themes
  (`:115–116`, `:155–156`), whose only consumer was `.band-invite`; and
  `wash-quiet` / `wash-quiet-fg` (`:111–112`, `:151–152`), whose only consumer
  anywhere was `.band` at `:211`. Regenerate with `tools/gen-tokens.sh`.

`--wash-feature` and `--wash-feature-fg` **stay**: `.notice`
(`brolly.css:481`) uses them, and it is unrelated to the landing page.
`--illustration-blend` and `--illustration-filter` lose their only consumer with
`.hero-figure img`; they are cheap to keep and will be wanted by any future
illustration, so they stay in the config and simply go unreferenced.

### The favicon stays

`base.html:9–11` links three files under `/static/favicon/`, and they are
Brolly's mark. The argument that removes `brolly.png` does apply, at reduced
scale — but a per-instance favicon means an asset-upload path, which means an
admin content surface, which is an explicit non-goal above. A 16px tab icon is a
different order of branding from a 200px illustration at the centre of the front
page. It stays, and is listed under Open questions rather than pretended away.

## Testing

The §4.5 invariants apply automatically and are expected to pass unmodified.

**Existing tests that contradict this spec**, all in `server/tests/auth_flow.rs`,
and what happens to each:

| Test | Disposition |
|---|---|
| `:431 the_landing_page_knows_you_are_signed_in` | rewritten: asserts 303 to `/account` instead of 200 with "Log out" |
| `:456 the_landing_page_still_invites_anonymous_visitors_in` | rewritten against the door — the instance name and the login form, not the old CTA copy |
| `:471 a_stale_session_cookie_falls_back_to_the_anonymous_front_door` | kept, retargeted: a stale cookie still reaches the door rather than bouncing |

`a_valid_invite_registers_and_logs_in` (`:150`) and
`login_succeeds_and_sets_a_session` (`:250`) assert only `SEE_OTHER` and never
inspect `Location`, so re-aiming those two redirects at `/account` does not
touch them.

The `get_as` helper (`:73`) returns `(StatusCode, String)` and drops headers,
unlike `post` (`:43`) which already surfaces `Set-Cookie`. The new redirect
assertions need `Location`, so `get_as` is extended first.

New assertions:

| Assertion | Why |
|---|---|
| `/` renders `instance_name` and `instance_description` | the description reaching a human is goal 2, and it has never been true |
| `/` and `/login` render byte-identical bodies for an anonymous visitor | one template, and the thing that keeps them from drifting |
| A signed-in GET of `/` and of `/login` both 303 to `/account` | both routes, because only testing `/` is how the other one rots |
| The door emits no `.shell-header` and no `.shell-footer` | the block overrides are the feature |
| `/register` renders the door, not the shell | the seam this spec exists to close |
| The door has exactly one `<h1>` and it holds the instance name | the invariant counts, but not which one won |
| Unset `BROLLY_TERMS_URL` omits the link rather than rendering an empty `href` | a dead link is worse than no link |
| The source link renders on both the door and the footer with no configuration | AGPL §13; it has no unset state, and it has two surfaces |
| None of `auth.html`, `base.html` or `_fine_print.html` contains the **case-sensitive** strings `"Brolly"`, `"Solid"`, `"ATProto"` or `"ActivityPub"` | the guard, scoped to the templates every visitor sees |

Case sensitivity is not a detail: `base.html:8` links `server/static/brolly.css` and
`:9–11` link `/static/favicon/…`, so a case-insensitive match on "brolly" fails
on day one against filenames that must keep their names.

`_fine_print.html` is inside the guard's scope even though it has no protocol
copy today, because it is the most natural place for someone to later add "this
server speaks Solid" as a helpful footer note.

The guard has a known gap: the door's heading, intro and alt-link text are Rust
string literals in `login_page` (`auth.rs:125`) and `register_page` (`:150`) —
the invite-only intro at `:159` is one — and a scan of `server/templates/` never
sees them. Extending the guard to those literals is possible but brittle; the
gap is recorded here so that whoever adds "we speak Solid" to an `intro` and
watches the tests pass knows it was a hole and not a permission.

That guard is a rule rather than a test of behaviour, and its scope is the
point. The protocol cards are a plausible, well-meant addition — "a member might
want to know whether their Mastodon client works here" — and they are how the
front page becomes a pitch again a year from now. Scoping it to the three
unauthenticated templates lets the authenticated surface keep saying "point a
Solid app here," which is instruction and belongs.

## Open questions

- **`BROLLY_SOURCE_URL` does not yet discharge §13.** Set provisionally to
  `https://www.brolly.id` (nk, 2026-09-11), which is the flagship instance's
  member app rather than a source repository — brolly.id's readme maps
  `www.brolly.id` to `member.app`. So the link is currently no better than the
  `https://github.com/` it replaces; it is a nicer domain, not a discharge.

  This is deliberate and temporary: the mechanism is what the door needed, and
  the value is one line. It stops being an open question when there is a public
  repository to point at, or a page at that domain that actually offers the
  Corresponding Source. Until then an operator who takes the obligation
  seriously should set the variable themselves, which is exactly why it is a
  variable.
- **The favicon is the last brand mark.** Settling it properly needs an
  asset-upload story, which is a non-goal here. Worth revisiting when the admin
  console grows any content surface at all — and worth refusing again if it
  doesn't.
- **What does `alice.brolly.id/` serve?** The door, until ADR 0010's promised
  server-rendered profile page exists. Unchanged by this spec, but now written
  down rather than incidental.
- **Where does `/consent` sit?** OAuth consent is rendered to a signed-in user,
  so by the rule above it belongs in the shell. But it is an interstitial in
  somebody else's flow rather than a page in this product, and the door's
  two-panel shape — requesting app on the left, decision on the right — fits it
  better than a dashboard tab does. Deferred; it is not on this spec's path.
- **Does the left panel need the description on `/register`?** The register form
  already carries "This server is invite-only" as its intro, and the description
  may read as redundant beside it. Cheap to settle once it is on screen.
